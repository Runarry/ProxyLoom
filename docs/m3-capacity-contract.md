# M3 容量基线与测量契约

需求基线为 10,000 节点、500 条链、200 组订阅；纯编译采用 500 个展开出站和 2,000 条规则，100 次重复输出必须一致。管理 API 使用 10 并发、20 分钟稳态；已发布订阅使用 50 并发、至少 1 MiB 的实际产物，记录精确字节数、错误率、延迟和 TTFB 分布。

预检发现既有 IR/API 将单路由方案限制为 1,000 条，无法容纳 NFR-03 的 2,000 条基线。M3 将该上限同步到需求 §7.1 的 10,000 条基础规则；系统设置仍可施加更低限额。追加迁移 24 记录应用兼容边界，使旧的 Schema 23 镜像不能回退读取超出其解析范围的新数据。旧修订不重写，不增加不相关的协议或路由语法。

容量验收使用真实生产 API、Runner 和 PostgreSQL 容器，数据由目录存储接口生成，发布仍通过正常队列与真实内核检查。纯编译单独计时；数据准备、内核校验和排队不计入纯编译时长。接口负载遍历分页游标；订阅读取逐次校验字节数与摘要，不能用混合或截断字节提高成绩。

实测宿主上限为 4 vCPU / 6 GiB，低于建议的 8 GiB 内存。API 上限 2 vCPU / 512 MiB，数据库 1 vCPU / 1 GiB，Runner 2 vCPU / 1 GiB；CPU 上限共享宿主，不是相加的资源预留。管理分页固定 100 条，不能通过减小分页或并发让指标通过。

预检暴露了订阅列表逐条读取发布状态、读取资源时重复规范化的问题。列表现在在同一只读快照批量查询发布状态；目录读取直接验证写入时绑定的原始明文字节 HMAC，再执行完整类型及 Schema 解码。发布安全依赖与实时授权查询保留，普通编辑和凭证轮换的不同处理由实库正反例覆盖。

`scripts/verify-deployment.mjs <镜像导出目录> --capacity=10` 仅为短时预检，报告 `baseline_run=false`，每个内核编译 5 次以加快定位。正式基线使用 `--capacity`（每内核 100 次编译、1,200 秒管理负载及 120 秒订阅读取负载），报告 `baseline_run=true`。没有完成规定持续时间、出现请求错误或 P95 超标，均不计为通过。测试只使用隔离合成数据，关闭公网测速。

订阅读取对编译产物复用 JSON 解码后的加密信封，最多 32 项 / 32 MiB，按最近使用淘汰。缓存不存明文或主密钥，不缓存授权结果；每次仍查询数据库，按当前信封与密钥包装的完整 SHA-256 选取缓存，并重新执行 AEAD 解密和内容 HMAC 校验。数据库故障、撤销、密文损坏和换包均不能由缓存绕过。

恢复演练选取最后一次备份，避免误用规模数据准备前的旧备份。完整结果应写入 T-058 证据，再逐项映射到 G3；arm64 继续保留未验，不由 amd64 指标推断其性能。
