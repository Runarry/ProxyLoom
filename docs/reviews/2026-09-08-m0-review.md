## 审查发现

### R1 · P1：回收一个任务会杀死另一个活动任务的后代

位置：`internal/runner/exec/proc_unix.go:44–57`，特别是第 46 行；同文件 `childrenOfSelfLocked`。

Linux subreaper 开启后，任务 A 的中间子进程退出，其后代 C 会被 Runner 收养。只要 C 不是登记的根 PID，`childrenOfSelfLocked` 就将它列入回收范围，即使 A 的根进程仍运行、C 仍属于 A 的进程组。任务 B 完成或超时触发 `reapOrphans` 时，先对 C 无条件发送 SIGKILL，随后才检查进程组是否属于活动任务；该检查已经无法保护 C。

复现：在一次性 Linux Docker 容器中启动持续运行的 A，由其短寿命中间进程生成 C，再让 B 超时。C 在取消 A 之前被杀死。临时复现包 `.cache/review-runner/exec` 的生产代码副本未改动，`proc_unix.go` 与仓库文件 SHA-256 相同。新增的复现测试 `TestReviewReapKillsAdoptedDescendantOfLiveRun` 断言错误行为存在，因此该复现测试显示 PASS 代表 BUG 被复现，不能当作正确性回归通过。

影响：不同执行任务相互干扰，造成错误连通性结果或异常中断。现有两任务取消测试没有覆盖“活动根进程＋被收养后代”。

建议：将回收范围绑定到结束任务的所有权；对仍属于活动任务的后代，在单 PID kill 和 wait 之前就予以保护；同时防止收割非 Runner 所有的进程。补充活动任务与结束任务并行、后代被收养、取消/超时等真实 Linux 回归。不要只移动进程组 kill 而遗漏单 PID kill。归入 T-040/T-028 修复，进入持久调度和 T-041 前必须解决。

### R2 · P2：能力目录浅拷贝污染后续加载结果

位置：`internal/capability/catalog.go:96–108`、`internal/capability/parse.go:245–253`；同类访问路径包括 Lookup。

Build 包含 `Capabilities []Record`，Builds/Build/Lookup 与 Catalog.clone 只复制外层结构。调用方修改返回 Build 的能力记录，会同时改变当前 Catalog 和 Load 的缓存源。后续新的 Load 也读到被修改的能力状态。

本次实测：临时程序 `.cache/review-capability/main.go` 执行 Load → Builds → 修改首条返回记录的 State → 当前 Capability → 新 Load 的 Capability，输出：

```text
before=unverified same_load=verified fresh_load=verified
```

影响：编译器可能漏发 `CAPABILITY_UNVERIFIED`、漏记未验证能力。当前没有发布路径，所以不将其描述为已经发生的发布绕过；它会在后续能力维护和发布判断中放大。

建议：所有目录快照和访问器深拷贝能力记录及嵌套 FixtureIDs 等切片，或者提供真正不可变的接口；增加修改返回值后原目录及下一次 Load 不变的回归。归入 T-023 修复，能力目录接入后续业务前完成。

### R3 · P2：生命周期验证忽略清理错误，产生假通过

位置：`internal/chainverify/core.go:251–261`、`internal/chainverify/live_test.go:477–495`、`539–544`，以及多个 `defer session.stop()`。

`stop()` 将监听未释放等错误放入返回的 `runResult.err`，但调用方经常丢弃整个返回值；lifecycle 中的部分结果被 `_ = res` 丢弃，取消分支只检查 Canceled。工作目录 Close 的错误在 stop 内也被忽略。现有某些显式检查能捕获一部分清理问题，但不能保证清理错误导致场景失败。

本次故障注入：通过 Go overlay 创建临时编译副本，仅在 stop 返回前设置 `res.err = fmt.Errorf("REVIEW_INJECTED_CLEANUP_FAILURE")`，不改变仓库源码或实际内核配置。在隔离容器运行三个内核的 lifecycle 子用例，三者全部 PASS，报告也全部记录 pass。临时 overlay 和报告位于 `.cache/review-lifecycle/`。

影响：T-028 的生命周期 pass 不能完整证明无清理错误；这不是已证明生产内核残留，而是已证明验收会吞掉失败。

建议：统一使用能向 testing.T 报告失败的清理函数，检查 Run/Close/端口关闭结果；预期取消和超时不应掩盖额外清理错误。补故障注入负例，并将实际失败反映到报告。归入 T-028，G0 评审前补齐。

### R4 · P2：Compose 烟测会复用并删除同名已停止资源

位置：`scripts/verify-isolation-compose.mjs:9`、`59–62`、`131–134`。

脚本固定使用 `proxyloom-isolation-t028`，仅通过 `compose ps -q` 检查已有容器。Docker Compose 的 `--all` 才包含已停止容器；已有项目仅有 stopped/exited 容器时会绕过此检查。随后 up 会复用/重建它们，finally 中的 `down --remove-orphans` 会删除非本次新建的容器或同项目孤儿。

证据：代码路径与本机 `docker compose ps --help` 已核对。没有为了复现而创建或删除用户的已有资源。本次真实烟测运行前另行用 `docker ps -a` 和 network label 核对该项目为空，执行后也确认无剩余容器。

建议：参考 `scripts/smoke.ps1`，使用本轮唯一项目名；启动前检查该名字下所有容器状态及网络/卷，查询失败时拒绝继续；清理仅针对确认属于本轮的资源。归入 T-053/T-028 测试脚本修复。
