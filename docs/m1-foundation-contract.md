## 2. 资源仓储与事务契约

仓储操作显式传入 scope。P0 的 scope 从服务配置或后续认证上下文取得，不接受请求任意指定工作空间。资源 ID、修订和 epoch 由应用服务生成或推进，创建请求不得自选 head、security_epoch 或 catalog_revision。

接口行为清单：

- 创建：接受名称、标签、enabled 与已验证的 Node／Chain 载荷，生成稳定 UUID、修订 1 与 epoch 1；同事务写入头、密文修订、DEK 包装、标签及引用。
- 读取：当前读取与指定修订读取分开。历史读取返回当时完整 metadata 与 payload，不能混入当前名称、标签、enabled 或 epoch。旧修订可用于受鉴权的历史查看，不能直接当作新发布的可用性判断。
- 条件更新：调用方提供 expected_revision。事务内读旧修订、应用类型化更新、重新验证载荷及引用，生成下一修订。不得由调用方提交“这是普通编辑”来绕过安全差异判断。
- 软删除／强制撤销：校验 expected_revision；保留历史数据与引用。删除设置 deleted_at、关闭当前资源并推进 security_epoch；强制撤销即使内容相同也推进修订和 epoch。
- 列表／标签／反向引用：限定 scope，使用稳定排序和有界分页；反向引用结果区分当前活动引用与历史修订引用。

写事务锁顺序固定为 scope → 按规范 UUID 排序的相关资源 → 修订及引用。资源种类与 scope 不可原地改变。成功的业务变更事务使 catalog_revision 增加一次，失败或幂等重放不增加。认证差异比较完整类型化 auth，包含认证类型及其字段；停用、删除、认证改变与强制撤销增加 epoch，重新启用不能恢复旧 epoch。

scopes、resources、resource_revisions、resource_refs、resource_tags 使用追加迁移建立。延迟约束确保提交时资源有合法 head；引用检查必须覆盖浮动引用与固定修订引用的存在性、scope 和 expected_kind。历史修订、历史引用不允许 UPDATE／级联删除。当前标签表为查询索引，完整历史标签同时保存在修订密文中。

已有 NodeRef 编辑态跟随节点头，写入的 Chain 引用从载荷中提取，不接受第二份由 API 任意提交的 refs 事实源。target_revision 的数据库约束支持固定引用，但不为现有 IR 添加未约定的编辑态固定修订字段。

存储错误转换为固定领域错误，区分不存在、修订冲突、引用无效、不可用数据库与加密失败；不得将 pgx 错误、SQL 参数、Schema 原始错误或密文载荷直接回传。

## 3. 加密、重包与秘密更新

加密组件暴露 Seal、Open、Rewrap 及按用途计算内容 HMAC 的内部接口。输入上下文包含 scope_id、table、object_id、revision、schema_version；上下文采用固定字段顺序的规范编码，不能使用有分隔符歧义的字符串拼接。仅允许内部定义的表名与用途。

Seal 返回两个分离的值：

- 不可变载荷：格式版本、AES-256-GCM nonce、业务密文及认证 tag。
- 可轮换包装：包装格式版本、key_id、独立包装 nonce、主密钥加密的随机 DEK 及认证 tag。

两层认证绑定相同对象上下文，并区分 payload／DEK 用途。每个记录生成新 DEK 和 nonce，不使用时间、对象 ID 或修订推导 nonce。解密必须先验证版本、上下文及认证，再交给严格 IR 解码；错误输出不区分能被用来探测秘密的底层细节。

不可变业务载荷与 content_hmac 留在 resource_revisions；包装记录独立存储并通过 resource_id＋revision 引用修订。重包只更换包装记录，事务更新时比较旧包装版本，不能覆盖并发轮换。它不重写修订密文，不推进 head、catalog_revision 或 security_epoch。

现有三个 32 字节文件密钥继续分别服务于主密钥、token pepper 与内容 HMAC；不同用途不得复用相同原始密钥。包装记录使用显式 key_id，轮换期间旧 key_id 必须仍可解析，缺少任何所需密钥时拒绝解密，不生成替代密钥。旧密钥的最终退役属于后续受控运维流程，不能由一次重包自动删除。

资源 content_hmac 对规范化的完整资源快照计算，集合 tags 排序，有序 hops／ALPN 保序；随机加密不影响该摘要。节点连接语义的去重摘要与请求幂等摘要使用不同用途标识，不能直接复用完整修订摘要。

管理 DTO 与完整 IR 分开。秘密补丁保留“缺省／null／字符串”三态：缺省保留、null 清除、字符串替换。完成类型化合并后再验证协议约束，必填认证被清除时返回 422；常见掩码与空密码仍按现有 IR 校验拒绝。所有认证秘密（密码、UUID、用户名等）统一应用此边界，不只保护名为 password 的字段。

响应 DTO 使用已配置状态表示秘密存在性；内部允许显式序列化完整 IR，仅用于加密或编译。普通响应、审计、错误和日志禁止序列化完整 IR。

## 4. HTTP 与幂等契约

管理接口前缀为 /api/v1，Runner 接口为独立 mTLS 监听器下的 /internal/v1，订阅为 /s/{token}/{target_key}。OpenAPI 3.1 逐项覆盖 SDD §10 的接口，不用成功空响应代替未实现业务；请求和响应定义与未来处理器实现状态分开记录。

严格解码拒绝未知字段、重复键、尾随 JSON、非法 Unicode 和不允许的 null；保留现有 IR 对版本、整数与联合类型的校验能力。错误体沿用 error.code／message／details 与 request_id，details 仅包含安全字段路径及通过校验的资源 ID，不回显非法字段名或输入值。

ETag 为强标签 "r<N>"；受版本控制的写入缺 If-Match 返回 428，合法但过期返回 412，格式错误返回 400，业务状态与幂等冲突返回 409。创建和没有资源修订语义的认证操作不套用资源 If-Match。

HTTP 中修订、epoch、generation、lease_seq 与事件 seq 等 int64 值使用规范十进制字符串（Revision 为正，Counter 允许 0，上限 int64）；内部 IR／catalog／PostgreSQL 类型不变。转换集中在 API DTO，不能把内部 Receipt／Metadata 直接输出为前端 JSON number。

分页 limit 默认 50、最大 200，created_at 与 ID 稳定排序。游标认证绑定 scope、资源集合、排序及规范化筛选摘要；改变筛选后不能复用。签名采用专用用途，不复用令牌验证值。权限检查仍由每个业务请求执行，游标不能承载授权。

幂等组件接受已认证主体、scope、固定路由标识、key、规范化请求与事务回调。唯一约束按主体＋路由＋key；并发相同请求等待获胜事务后重放，相同 key 不同请求返回 409。事务回调使用与幂等登记同一事务的仓储，不能自行启动并提交第二个事务；业务失败回滚幂等登记。

持久记录只保存请求 HMAC 和允许重放的结构化元数据／响应引用，不接受任意原始响应字节。令牌签发等一次性秘密的重放只返回元数据。删除、过期和重放后的业务授权仍由对应处理器负责；通用组件不能成为绕过鉴权的响应缓存。

OpenAPI 还须明确：

- 发布确认绑定 batch_id、effective_preview_hash 及当前操作者；服务端校验，不能只由前端传字段即视为确认。
- 测试父批次列出子任务、汇总状态与取消语义；jobs 状态与 pass／fail／inconclusive verdict 分开。
- Runner heartbeat／event／result 携带 job_id、attempt、lease_seq；API Worker 与 Runner 的任务类型分离，来源抓取和纯编译不由 Runner 领取。
- SSE 使用稳定事件序号和 Last-Event-ID，超出重放窗口返回重新读取快照信号；不流式返回原始 stdout。

sqlc 与 openapi-typescript 在实际引入时锁定可取得的精确版本与校验信息，禁止 latest。TS 类型从本地 OpenAPI 生成，Go DTO 使用相同契约夹具验证；生成检查在临时目录重建并比较，不能静默改写受检源码。

## 5. 集成验收与状态

真实 PostgreSQL 验收涵盖从空库／现有 bootstrap 升级、迁移重入、约束、权限、并发写入、幂等与回滚。夹具只使用合成节点、凭证和临时密钥，不接触现有开发卷或真实秘密。

完整服务级场景为：创建 A／B → 创建 A→B → 改名与标签 → 读取旧修订 → 并发条件编辑 → 认证轮换 → 软删除与反向引用 → 主密钥重包 → 核对明文、HMAC、revision／epoch／catalog_revision 的变化范围。

失败场景须覆盖逐个 AAD 字段替换、错钥、篡改、失钥、无头提交、跨 scope／错误 kind／缺失修订引用、历史修改、过期版本、同键异体、并发幂等、秘密清除后认证不完整及日志扫描。

证据归入 T-004／T-005／T-007，保存源码清单、工具锁、命令、测试环境与结果。本窗不实施 T-006／T-008 的完整范围，但必须在现有工程入口中接入本窗自身所需检查。代码与自动验证齐备后进入 in_review，不能自动 done 或宣称完整 G1 通过。
